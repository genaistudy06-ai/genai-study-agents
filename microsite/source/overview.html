01 The problem

Scanners find thousands of issues. Teams fix the wrong ones first.

Everlit isn't another dependency updater or scanner. We keep the scanners we have; Everlit adds what they leave out: business context, policy, enforcement at the pull request, and fixes that are proven in CI.

Update bots don't know what's exploitable

Dependency-update bots keep packages current by opening an upgrade PR for every outdated package. None of them says which upgrade closes a vulnerability attackers are using today, or which service it matters for.

EPSS likelihood and the CISA KEV list feed every score.

Generic severity ignores our context

A CVSS 9.8 in a test helper and the same bug in an internet-facing payments API get the same label.

Import evidence, exposure and criticality reshape priority.

Post-merge scanning is too late

By the time a nightly scan flags it, vulnerable code is already on main and heading to production.

A pre-merge gate blocks only what the PR introduces, and an AI review flags risky code before it reaches main.

How Everlit compares

Everlit sits on top of the scanners, not in place of them. Update bots keep packages current, scanners find issues, and commercial risk platforms pull findings into one view; Everlit adds our context, the pull request gate and fixes proven by a rescan. It is slower to start and our own team supports it. See the full build-versus-buy comparison →

      06 The final check

      "Did the fix actually work?" Only a rescan gets to say yes.

      After the merge, Everlit reconciles the next scan against what it knew. Pick what the rescan sees; these are the platform's real auto-close rules.

      07 Proof you can check

      Every claim comes with its receipt.

      A dashboard that says "0 findings" is only as good as what it looked at. Everlit records what each scan checked, where each score input came from, which policy decided, and who signed off, in a log nobody can quietly edit.

      Coverage receipt on every scan

      Manifests and dependencies checked, whether OSV.dev answered for every package, EPSS and KEV freshness, and the policy version. A finding only auto-closes when coverage is complete.

      Every score input labelled

      Each term of the priority score is marked Verified, Inferred, Declared or Default, with a confidence line and the exact arithmetic. A guessed number never looks like a measured one.

      Policy versions

      The rules, merge-blocking settings and deadlines are hashed into a version. Scans, gate verdicts and decisions record it, and any version expands back to its exact rules.

      Tamper-evident audit log

      Each event stores a SHA-256 hash of the event before it. One click verifies the chain; an edited or deleted entry is named exactly. Exports carry the hashes.

      Verified, not just merged

      Branch, CI, PR, merge, then the rescan that proves it: each step is timestamped. Closed PRs, cancelled fixes and repos that never report CI are shown as what they are.

      Accountable sign-off

      Exceptions, gate overrides and not-affected statements all need a second person. Sessions end after 8 hours or 30 minutes idle, per device, and gate evidence is kept 400 days.

      08 AI with guardrails

      AI investigates and explains. The rules decide.

      Every AI feature reads a defined slice of evidence, cites what it used and writes a record of the run. None of them can change a status, a score, a verdict or a deadline.

      Investigate a finding

      Facts with their source, the unknowns said out loud, a recommended next step and a confidence level.

      Explain a verdict

      Why a PR was blocked, in the score's own terms and the rule that matched, with the options to move forward.

      Release notes and CI triage

      What a version bump changes, and whether a failed CI run was caused by the bump.

      Rules in plain language

      Describe a rule; the AI drafts it in the engine's own fields and a simulation shows its effect before a person saves it.

      AI can

      • Read the finding, the PR diff or the history it was asked about
      • Draft explanations, summaries, rules and exception text
      • Flag weak or repeated exceptions for a person to review

      AI can never

      • Change a status, score, verdict or deadline
      • Approve exceptions, overrides or VEX statements
      • Follow instructions found in code, advisories or tickets

      Every run

      • Is logged with model deployment, prompt version and the evidence it read
      • Treats repository and advisory text as data, never as instructions
      • Stays inside our approved model deployment and one tenant's data
      09 Across the portfolio

      From one finding to the whole estate.

      The same evidence that ranks one finding also shows where else the package lives, which single upgrade removes the most risk, and what a release shipped with.

      Blast radius

      Every repo where a vulnerable package lives, with its exposure, criticality and owning team.

      Remediation plan

      Shared upgrades ranked by the risk they remove across repos, with the patch, minor or major change each needs.

      Root causes

      Packages vulnerable in several repos, exceptions renewed again and again, and fixes that need engineering time.

      Release passport

      One file per release: inventory, coverage, verdicts, exceptions with owners, verified fixes and the policy version.

      SBOMs from CI

      CI posts the CycloneDX or SPDX SBOM of each build, so the scan matches exactly what shipped.

      VEX with evidence

      Not-affected statements need evidence and a second approver, and flow into every VEX export.

      KEV re-scoring

      When CISA lists a CVE, matching findings are re-scored and their deadlines tightened at the next daily sync, with no rescan.

      Where teams work

      GitHub check runs with annotations, Slack alerts to the owning team, and Jira or ServiceNow records for work that needs a plan.
